# 随项目积累的个人技能更新

适用：用户要求“更新这个 skill”“把 milestone 设计/最终实验/新偏好沉淀进去”“将这个项目变成以后可复用的经验”。当前任务明确要求更新时直接完成，不再逐条索取批准。

目标是让个人规则更准确、参考案例更丰富，同时保持入口和默认上下文简洁。

## 1. 三层内容，各有位置

| 层次 | 放什么 | 更新位置 |
|---|---|---|
| 个人规则 | 用户明确偏好、经过选择的可覆盖工作习惯 | [个人档案](personal-profile.md)；仅普遍影响执行的规则进入主入口 |
| 参考案例 | 用户采用的阶段设计过程、最终实验、关键取舍与可迁移方法 | 每项目按需建立阶段设计 PCASE 和最终实验 E 案例，分别索引并关联；使用[阶段案例模板](../assets/milestone-case-template.md)或[实验案例模板](../assets/experiment-case-template.md) |
| 项目事实 | 参数、原始结果、临时约束、运行状态、详细调试日志 | 当前项目记忆/数据；只把理解案例所需部分带入 skill |

通用阶段手册保存操作方法，不重复粘贴每个案例。同一条“保留负结果”“核对最终包”已有规则时，更新来源或适用条件，不新增一份同义要求。

## 2. 找到本次沉淀的权威材料

沉淀 milestone 时读取初始想法、当时协议、实际阶段报告及后续决策，恢复“当时知道什么—为何这样验证—得到什么—怎样改变下一步”。区分事前计划、实际执行和事后总结，不能只从最终论文反推一条从未失败的开发路线。后续事实纠正仍优先于旧记录；保留旧材料在当时的用途。

沉淀最终实验时，先看用户指定的最终稿/报告，再核对实际章节、引用图表、结果及最近纠正。不能根据所有 runs 目录、最早计划或最好看的数字自行推断“用户最终选择”。

若用户明确给出最终版本，直接采用。尚未定稿时可以保存带状态的“候选案例”，不得写成已选。无法从材料解决且影响取舍时，只询问哪份版本/哪组实验；其余整理继续。

记录最终选择相对研发过程的取舍：哪些成为主实验、哪些作为辅助/补充、哪些尚未实施。主文没有采用不等于数据作废，也不能自动删除对结论有影响的反例。

## 3. 提炼设计逻辑，而非复制项目日志

每个重要 milestone 提炼：

1. 前序留下的关键未知项，以及它阻碍的下一能力。
2. 选择这一最小范围/验证形态的原因、已有依赖和明确保持的条件。
3. 事前判据、实际验证及产物；分别记录实现、检验与假设支持状态。
4. 失败、反例、修订如何影响判断，以及为什么改成下一阶段或独立分支。
5. 能移植到新对象的设计动作、适用范围及不能照搬的参数。

使用阶段案例模板建立自包含过程案例，并与同项目实验案例关联。尚未发生的后继方向保留为计划；更好看的分支不覆盖旧条件下的结论。新项目若与已有经验不同，说明条件差异或修正原规则，不强行套成同一路线。

每组最终实验提炼：

1. 它要回答的一个问题，以及对核心贡献的作用。
2. 实际设置、比较/干预、选择规则和验证单位。
3. 数据与图表如何分工，结果如何形成可读的论证。
4. 这一设计有哪些值得迁移的动作、哪些条件只属于该项目。
5. 如果换一个研究对象，应替换哪些槽位。

保留能决定解释的数值与边界，不复制全部表格、原始日志、图片和私有数据。案例应自包含；原项目相对路径、日期和版本只作溯源。涉及分享时沿用用户的数据范围，不把仅本地可用材料默认为可公开。

## 4. 新经验如何进入个人规则

| 新内容 | 处理 |
|---|---|
| 用户明确“以后都这样” | 写入个人要求，记录具体作用域和来源 |
| 用户只为某图/某轮指定 | 记录在项目或案例，不扩大到所有项目 |
| 从最终成果观察到的习惯 | 作为可覆盖默认习惯，明确是提炼结果 |
| 新案例再次支持已有习惯 | 合并来源，必要时细化适用范围 |
| 新要求与旧规则冲突 | 依据明确范围和最新指示替代/分支，写明旧项状态 |
| 仅实验结果变好/变坏 | 更新案例事实，不直接转成永久流程要求 |

保持规则 ID 稳定。个人偏好与科研事实分别管理：偏好可以决定怎样组织表达，不能更改已经发生的实验或数值。

## 5. 实施更新与避免版本漂移

1. 定位本次实际调用的 skill 目录与用户指定维护源。跨项目时先读取当前已安装内容，不拿旧项目发布目录覆盖较新的个人版本。
2. 若同时存在维护源、安装副本和 ZIP，比较内容/版本；有不一致先保存并合并有效变更，再选一个本轮编辑源。不要同时独立编辑多份。
3. 保存更新前可回退副本，放 skill 目录之外；沿用已有版本管理。按需新增阶段设计/实验案例、更新个人索引及相关路由，改动范围尽量小。
4. 按需增加版本或日期，保留简短的变化说明；不让更新日志和重复历史占满常用入口。
5. 检查 frontmatter、链接、案例出处和术语；核对每个新条目可从入口发现且不依赖旧工作区才能理解。
6. 只有路由/行为有实质变化时做针对性试用；只添加一个已核实案例不必重新测试所有阶段。
7. 同步本轮维护源、个人安装目录和分发 ZIP，比较文件清单与内容。安装目录若在过程中被其他任务修改，先合并，不能直接覆盖。

遵守实际文件系统权限。某个同步位置暂不可写时，保留已经完成的工作副本并说明具体位置与未同步状态，不假装全局版本已更新。

## 6. 普通项目中的积累方式

日常将“本轮值得复用的经验”放在项目记忆的候选区：内容、来源、适用范围、拟新增/修正什么。无需每发现一条就打断用户。

用户要求更新 skill 时，把这些候选与最终采用成果一起筛选、合并。若已有明确的项目收尾自动更新约定，则在该范围内执行；本流程本身不创建自动后台更新或跨项目任务。

可以由用户一句话触发：

> 把这个项目的 milestone 设计与转折、最终选定实验、我新确认的习惯更新进 $ai-research-project，合并已有规则并同步个人版本。

## 7. 完成后只交代有效变化

给出更新后的 skill/重点案例/分发包，说明新增了哪个参考、哪些习惯变化、哪些仍只属项目。确认安装副本与发布包是否同步，并注明实际验证。

不要宣称“今后自动永久记住”。跨项目复用依赖可读取的个人 skill 和项目记录；本轮应把已授权的内容真正写入这些载体。
