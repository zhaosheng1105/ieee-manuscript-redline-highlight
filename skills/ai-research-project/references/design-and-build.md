# 研究定位、技术设计与最小系统

适用：从方向到问题、从问题到方法、从既有工程到可运行链。实现深度服从当前任务。

需要把这些工作拆成逐级验收的 milestone，或决定阶段结果之后怎样推进时，读[阶段设计与验证](milestone-design-and-validation.md)；具体路线变化参见[PCASE01 设计案例](milestone-case-thermal-tire-ggv.md)。

## 将想法改写成可检验问题

区分应用需要、现有方案缺口、拟提出机制和验证机制所需证据。可用工作句：

> 在【条件】下，现有【方法/流程】受到【障碍】限制。通过【机制】实现【可观察能力】，用【实验/交付】检验其相对【替代方案】的价值和代价。

“使用 AI/世界模型/强化学习”是技术选择，不自动构成贡献。“没人做过”需要检索核实，不能从未找到材料推出。

| 主张 | 最小支持 | 不足以支持的材料 |
|---|---|---|
| 新能力 | 可复现完成能力及必要条件 | 架构图新增模块 |
| 机制有效 | 机制参与实际决策，移除/改变它影响目标行为 | 仅内部变量变化 |
| 比已有方案更好 | 同口径、条件和预算下合理对照 | 最弱基线或单个最好案例 |
| 泛化/迁移 | 明确新条件、冻结/适应项及独立评价 | 用目标测试数据调参后再测试 |
| 降低成本 | 界定成本并完整计入 | 只报告训练/配置后的性能 |

选择最有证据潜力且可完成的主线；其他方向留待后续，不让第一阶段同时承担所有贡献。

## 文献服务于决策

需要检索时，查最接近的方法、强替代方案和关键定义，优先原论文、官方资料及数据集说明。记录来源、条件、机制、证据及与本项目的关系。

回答：问题是否相同？输入和资源是否相同？作者验证了什么？增量是什么？哪项实验能区分两者？不要用标题/摘要相似度代替方法比较。

对元数据、引用和最新规则做真实核查；缺工具或全文时说明访问边界，不编造条目、DOI、原句或优先权。接续项目时无需重复已有有效检索。

## 建立最小运行链

输入：现有工程、环境、示例、数据和期望输出。

1. 找真实入口、运行依赖、外部服务、关键配置和已有检查。
2. 识别需改变的最小接口。必要时用隔离目录/工作树保护原工程，不要求所有项目复制一份。
3. 复现既有基线，再加入新变量；分开环境故障与方法失败。
4. 连通输入→核心处理→输出→可观察反馈，记录复现命令。
5. 建必要诊断日志，不为“完整架构”预造大量抽象层。

输出：最小版本、环境说明、配置、实际观测和已知缺口。

验收不能只看编译、进程存活或话题存在。仿真器启动不代表车辆移动；API 返回成功不代表请求生效。需要目标行为及关键因果链证据。

## 建立关键接口的数据约定

核对影响正确性的属性：

- 输入/输出含义、单位、坐标系、索引和时间基准。
- 采样频率、时延、有效期、缺失、重置和切换行为。
- 请求值、接受值、内部使用值、最终物理响应分别在哪里记录。
- 真实测量、代理量、人工标签、控制条件和预测的区别。
- 配置加载路径、缓存、旧安装副本和重复进程。
- 限幅、插值、饱和、保护或后处理如何改变实际执行。

例如请求倍率上升，但限幅后曲线未改变，不能认定高倍率已成功验证。温度设定、传感器温度和摩擦读回不能混为一个字段。这些是案例，不把车辆字段复制到无关领域。

## 用失败证据驱动调试

采用“现象→候选原因→区分检查→最小修复→原条件复测”。

| 现象 | 优先区分 | 修复后验证 |
|---|---|---|
| 没有输出 | 数据到达/新鲜度，入口是否真实加载 | 端到端行为恢复 |
| 数值异常 | 单位/坐标/时间，代理量与真实量 | 已知样例与有效区间 |
| 离线正常、在线失败 | 时序、阻塞、频率、实际参数 | 同类在线条件下完整闭环 |
| 配置修改无效果 | 旧副本、缓存、参数读回、限幅 | 内部使用值与实际响应 |
| 指标成功却无行为变化 | 是否只测代理对象或低需求区 | 目标对象是否受到有效作用 |

保留推翻原假说的证据。假说错误时撤回不必要修改，不放宽阈值、删除异常或重命名指标来制造通过。测试针对故障机制和真实不变量；低风险小编辑不必增加镜像测试。

观测权限或环境不完整时，区分“此会话没观察到”和“真实系统不存在”。可提供诊断入口并读取实际产物，不凭受限环境的空输出判定宿主系统故障。

## 从局部机制到完整系统

先选能隔离机制的小问题：新观测是否改变下一次决策？预测是否改变动作排序？状态保存后新进程能否正确复用？

局部成立后扩大覆盖和接口规模，重新检查时空边界、持久化、索引、一致性和资源开销。局部演示不能直接替代完整系统验收。

按功能记录方法身份：预测器、决策器、记忆更新、执行接口、保护器。历史 GRU、后来的区域树模型与分析脚本可以共存，但各自输入、训练数据、指标、部署位置须清楚。组件指标不能移给另一个实际运行模型。

## 复杂度升级由证据决定

结果不足时依次判断：

1. 数据、标签、接口是否可信？关键失败是否被错误丢弃？
2. 指标是否测到了目标机制，采集是否提供有效激励？
3. 模型已用于决策，还是只做单独评价？
4. 简单规则、记忆、局部修正能否先验证核心想法？
5. 复杂模型具体解决哪个瓶颈，怎样避免新混淆？

缺口是执行不一致时先修执行；缺口是探索成本时先测预算与复用收益，不默认换更大网络。路线改变要保存原因与版本，不将初始蓝图强行写成最终实现。

## 阶段结束的产物

- 一个核心问题及实际达到的能力。
- 代码/配置、命令、输入/输出与版本身份。
- 结果、失败案例及影响结论的条件。
- 未实现的最初设想，避免以后混入论文。
- 下一项关键不确定性与验收产物。

写回现有主记录。研究记录按时间保存认识演进，最终方法章节按读者需要的机制逻辑组织。
