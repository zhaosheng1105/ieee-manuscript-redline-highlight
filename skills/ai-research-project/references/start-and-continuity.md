# 启动与持续协作

适用：新项目、接手、换对话、需求纠偏和并行协作。目标是把“用户反复解释”变成“AI 主动读取和维护”。

## 新项目：先形成可执行的最小约定

从已有材料提取以下内容，只询问影响下一步的缺口，不一次发长问卷。

| 内容 | 要明确到什么程度 |
|---|---|
| 应用问题 | 谁在什么条件下遇到什么困难，现行办法为什么不足 |
| 最终用途 | 代码工具、演示、实验结论、论文、报告或其中几项 |
| 可观察成功 | 什么运行、指标、结果或交付意味着完成 |
| 现有资源 | 代码、数据、模型、设备、软件环境、论文和既有结果 |
| 约束 | 固定底座、不可改模块、算力/时间、数据权限、输出格式 |
| 首个里程碑 | 最小可运行链或最关键的可检验假设 |

先写简短项目判断，再做实际动作，如跑现有示例、检查字段、复现基线或建立数据到结果的链。目标不清但可逆探索有价值时，可以带着显式假设开展，不把假设写成用户已确认。

## 已有项目：按依赖读取

推荐顺序：当前指示/项目指令 → 当前入口与交接 → 最新阶段报告 → 直接相关代码和协议 → 必要原始证据。历史备份用于追溯差异。

| 材料类别 | 作用 | 容易发生的错误 |
|---|---|---|
| README/主记录 | 导航、运行入口、当前状态 | 把未同步的摘要当最后结论 |
| 设计/技术参考 | 理论、候选方案、接口意图 | 把设想当已实现 |
| 源码/配置 | 实际计算与版本条件 | 仅凭当前代码推断历史运行版本 |
| 日志/manifest | 一次执行及其条件 | 把复制分片计作独立样本 |
| 分析/作图脚本 | 数据到数字或图片的转换 | 把回放脚本用途当原实验部署事实 |
| 修订报告/作者确认 | 事实纠正、范围、权威稿 | 继续采纳已撤销判断 |
| PDF/ZIP/交付目录 | 用户实际使用的结果 | 临时目录完成却未同步交付位置 |

不能确定权威稿且会影响编辑时，先比较版本、入口引用和用户指示；仍有歧义只问该版本问题，无需重问整个项目。

## 项目记忆：当前、决策、证据

三类内容可放在同一记录的不同小节，不强制建立三份文件。

**当前状态**只保留仍生效内容：目标、范围、版本、阶段、可运行命令、交付入口、下一步。长度以快速恢复为准。

**决策记录**保存有后续影响的变化：日期、问题、采用方案、理由、依据、被替代方案和受影响产物。普通小修不必逐条写研究日志。

**证据索引**链接原始记录、配置、分析脚本、结果和图表，记录状态与适用条件，不复制全部数据。

可用状态：计划中、已实现未运行、已运行未核查、已核查、作者确认、本地材料未覆盖、被新证据替代。按需使用，避免过度细分。

## 保存用户要求的作用域

记录为：`要求｜作用域｜来源｜生效状态`。

- “后面都用中文解释”可能是持续偏好。
- “这一轮只改 III–VI”是本轮范围。
- “此图用单栏”属于图表/稿件约定，不能推成所有项目禁止双栏。
- “先不要跑新实验”约束本轮动作；后来明确要求执行时，核对是否已经改变边界。
- 用户纠正实验事实，要更新事实记录及依赖文字，不只在聊天中回答“明白”。

新事实与材料矛盾时，分别保留来源与适用范围。例如作者确认在线开环运行，本地有离线回放脚本，两者可以共存。脚本不能否定在线执行；作者确认也不能自动证明某数值、代码版本或运行延迟。

## 每轮执行闭环

1. 恢复目标、约束、上次状态。
2. 选能消除关键不确定性的下一项工作，明确验收信号。
3. 完成必要实现或分析，并行处理独立事项。
4. 检查实际输出，失败时依据证据定位。
5. 同步结果、最终路径和项目记忆。

长任务分阶段更新，不把每次更新变成审批。已授权范围内可逆的实现、检查和修复自行完成；需要用户输入的依赖，具体说明阻塞点并处理其余工作。

不要用相同参数反复重试没有新信息的失败。按问题设置合理尝试预算；连续失败且没有新诊断依据时，保留错误、最小复现、排除原因和具体下一步。

## 跨窗口交接

交接应让下一轮直接行动：

```text
当前目标与本轮范围：
权威入口与版本：
已完成及其证据：
持续约束/最近纠正：
下一项具体动作：
命令、输入路径与输出位置：
成功判据：
已知阻塞与失败现场：
不要重复的已完成工作：
```

运行中任务另记进程/会话标识、日志、结束条件和接管方式，不遗留只有聊天知道的后台状态。未执行的验证不能随交接变成“已通过”。历史指令明确标失效，当前状态置顶。

## 并行协作

- 委派单一可验收任务，给目的、输入、允许写入文件、输出格式和不能改变的条件。
- 适合并行：文献与代码对照、独立组件、图表来源检查、事实与语言审阅。
- 需要串行：共同口径修改、共享设备运行、正式协议变更、互相依赖的文件修改。
- 整合时检查冲突、术语、同名模型的版本身份及未验证断言；子智能体“完成”不代替集成检查。
- 行为测试给评估者真实任务和最少材料，不给预期结论；观察实际产物与操作选择。

## 有用的进度更新

新发现 → 对结论/执行的影响 → 下一步解决什么。

例：“请求参数与实际执行值在切换后短时间内不一致，会污染动作标签。我正在定位切换窗口，并用对齐后的标签进行评价。”

最后给最终文件和关键验证，写明实质缺口。不要用“全部完善”概括尚未验证的部署、独立复现或投稿状态。
