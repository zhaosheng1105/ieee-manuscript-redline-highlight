# Milestone 设计：逐步消除不确定性

适用：拆解研究路线、确定下一里程碑、判断阶段是否完成，以及根据真实结果调整设计。局部修复、单图修改等任务沿用原阶段即可，不额外建立一套路线。

用户明确重视本项目的逐级验证设计。参考[thermal_tire_ggv 设计案例](milestone-case-thermal-tire-ggv.md)，迁移的是“问题—最小验证—实际证据—下一决策”的关系；不照搬 M0–M5b 编号、赛车对象或实验参数。

## 1. 先画能力依赖，再排工作

从最终希望成立的能力反推：它依赖哪些尚未证实的事实？其中哪项一旦不成立，会使后续投入失去意义？先安排能以较小代价区分这些可能性的验证。

例如，自适应系统的证据依赖可能是：

```text
输入和反馈可信
  → 能表征动作后果
  → 信息能改变合理的选择
  → 选择被真实执行
  → 新反馈改变之后的行为
  → 扩大范围后仍成立，经验可以复用
  → 与合理替代方案相比，收益值得付出成本
  → 新条件/真实场景中成立到明确的范围
```

这不是固定工序。有些项目无需预测器，有些已有可靠执行平台；可以跳过已有证据充分的环节，或并行开发独立接口。新阶段所依赖的能力必须有对应证据，不能只因为前一阶段“做完了”就放行。

“写代码、训练模型、跑实验、写论文”描述工作类别，单独用作 milestone 无法判断研究是否前进。改成可以判定的问题，例如“模型能否区分本任务真正需要选择的候选”，再安排训练、采集和评价。

## 2. 分别管理两条线

| 线索 | 它管理什么 | 完成判断 |
|---|---|---|
| 实现与交付 | 数据管线、模型、接口、可运行程序、报告 | 产物存在且通过所需行为检查 |
| 研究证据 | 数据能否回答问题、机制是否参与、假设是否获得支持 | 预定检验产生可信结果，并明确支持/不支持/尚不能判断 |

训练完成可能只完成实现；一次正式比较也可能在假设未获支持时完成研究任务。将“实验已完成”和“假设被支持”分别记录。

**阶段收尾不等于所有后继阶段可用。** 若 M1 的候选排序未通过，可以收尾并设计替代机制；不能继续以“排序已验证”为前提部署原方案。依赖该能力的路径需要修复、补证据或明确替换前提。

## 3. 每阶段只优先解决一个关键问题

以下字段可并入现有项目记录，只有需要时才单独建阶段卡：

| 字段 | 需要写清的内容 |
|---|---|
| 为什么现在做 | 上一阶段留下什么不确定性，解决后会改变哪个决定 |
| 核心问题 | 可观察、可区分答案的一个问题，而非预先肯定的口号 |
| 进入条件 | 依赖哪些已验证能力，证据及版本在哪里 |
| 最小范围 | 先在哪个对象、局部条件或受控任务中检验，什么留给以后 |
| 改变与保持 | 本轮新增的机制/接口/条件，保留的基线与冻结资产 |
| 验证动作 | 什么输入、干预或对照能真正触发待检机制 |
| 判定方式 | 观测量、统计单位、必要阈值、失败/无效数据处理及依据 |
| 有界执行 | 所需资源、已有授权、预算和结束条件；按任务复杂度填写 |
| 验收产物 | 运行结果、完整事件、实际执行读回、复用或比较证据 |
| 分支决策 | 支持、部分支持、不支持或无法判断时分别怎样处理 |

阈值只在问题确实需要时设置，并说明工程容差、任务要求或统计设计依据；不能复制案例中的 1%、600 s、3 次或特定误差作为所有研究的验收值。

## 4. 用较小范围隔离机制，再扩大复杂度

按当前瓶颈选择验证形态，不要求每个项目把下表全部运行一遍：

| 验证形态 | 主要排除的问题 | 不能独自证明 |
|---|---|---|
| 数据与离线检查 | 字段、标签、划分、单位、实现是否可信 | 线上稳定运行或任务收益 |
| 回放/记录库决策 | 规则、信息可见性、记忆更新是否按预期发生 | 未实际执行候选的真实后果 |
| 只读在线输出 | 实时输入下能否产生有效及时的输出 | 输出已经接管执行或带来收益 |
| 局部真实干预 | 一个受控条件中，动作—反馈—后续决策是否连通 | 全范围覆盖、长期稳定或泛化 |
| 执行接口验证 | 下游实际采用的输入是否等于计划输入 | 机制带来更好的任务表现 |
| 完整流程与重启复用 | 局部机制能否集成，经验能否跨进程生效 | 相比强基线的净收益 |
| 冻结正式比较 | 共同条件/预算下的价值、代价及差异 | 另一初始化、另一场景的结论 |
| 新条件/真实场景 | 固定与变化部分之间的适用范围 | 未做过的控制方式或广泛泛化 |

一次代表性事件应穿过实际边界：候选/输入 → 下游实际采用 → 有效响应 → 状态/记忆变化 → 下一次选择 → 后续实际验证。检查日志能解释决策，还需区分它是否包含真实执行证据。

选择能有效检验机制的条件。干预未穿过限幅、低需求区域未激发能力、观测失效时，不能把“平稳完成”当作目标假设通过；也不能为了触发结果擅自扩大已授权操作。

## 5. 如何从结果决定下一阶段

| 本阶段发现 | 优先决定 | 下一阶段怎样设计 |
|---|---|---|
| 输入、标签或执行链错误 | 修复基础，保留失败现场 | 在原条件重验，再释放依赖该结果的工作 |
| 代理指标好，实际选择无改善 | 检查指标、时域、有效激励和决策用途 | 增加任务相关后果检验，必要时替换表征/模块 |
| 局部机制成立 | 扩大一个有意义的范围 | 核验新增接口、覆盖、耦合、持久化等具体风险 |
| 完整系统可运行但收益不足 | 分析知识获取、执行、恢复和部署成本 | 分开学习与利用，在新版本检验可区分的解释 |
| 正式对照未支持优势 | 收下该结论，重新选择问题或改进方向 | 冻结原结果；新方案新协议、新评价数据 |
| 证据不足或结果混合 | 指明缺哪个判别信息 | 补最能改变决定的验证，不直接增加所有实验 |
| 新分支改变初始知识或资源 | 把它作为另一条件/问题 | 显式保留该变化，不能用它替换旧条件下结论 |

优先检验结果支持的瓶颈，不将“换更大模型”作为所有负结果的默认响应。多个解释尚未区分时，把它们写成候选假说；不要将事后合理解释写成已测得的根因。

## 6. 路线随证据更新，执行保持连续

起步时给出粗粒度依赖路线，细化最近的一个可执行阶段和必要的后继接口即可；不要预写后续成功数据或把所有阶段锁成不可改的日程。

阶段结束时：

1. 对照原问题和判定方式，记录实际执行范围、实现状态及证据结论。
2. 保存可复用产物、版本、完整尝试和关键失败；正式评价后保留冻结版本。
3. 写清通过了哪些能力、哪些依赖尚未释放；旧计划的已替代内容显式更新。
4. 指定下一项不确定性、选择它的理由、最小动作和验收证据。
5. 在既有授权和资源范围内继续；用户要求阶段暂停时按该要求交接。

执行故障与算法结果分别记录。正式流程变更写修订依据，保留中断运行及适当敏感性分析；用正式测试结果开发的新版本，需要新的独立评价，不能循环使用同一测试集并保持原标签。

## 7. 研发路线与最终实验各有用途

milestone 解释“怎样一步步建立能力、发现问题并改变设计”；[精选实验](personal-profile.md)解释“最终怎样围绕贡献组织证据”。二者互相链接，不彼此替代。

一个正式实验可能使用多个 milestone 的有效产物；一个 milestone 也可能同时贡献主文、补充和复现材料。历史尝试没有成为主实验，不代表可以删除决定结论的负结果。论文按研究问题组织，不要求按 M0、M1、M2 顺序讲研发日志。

## 8. 新项目如何复用和积累

按“遇到何种瓶颈”检索[个人案例索引](personal-profile.md)：例如代理指标失配、局部到整体、接口生效、预算内收益或先验条件变化；不只按研究领域相似度选例。

设计时说明借用了哪种拆解、为何适用、哪些不适用；具体对象、实现、预算与判定另定。完整项目采用[项目记忆模板](../assets/project-memory-template.md)接续日常工作。

用户要求沉淀后，用[阶段设计案例模板](../assets/milestone-case-template.md)记录原始计划、当时证据、设计转折、实际结果和可迁移动作。新增独立案例 ID，与同项目最终实验案例关联；多项目支持同一习惯时合并来源，有差异时补适用条件。详见[技能更新流程](skill-evolution.md)。
