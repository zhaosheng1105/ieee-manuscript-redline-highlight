# 实验与证据

适用：采集、训练、机制验证、正式对照、迁移、仿真与实测。重点是让结果能回答原问题，且保留其成立条件。

## 个人实验参考优先入口

涉及设计、补充或组织实验章节时，先查[个人偏好与精选实验索引](personal-profile.md)，再读适用案例。当前优先参考[thermal_tire_ggv 最终选定实验](selected-experiments-thermal-tire-ggv.md)，以最终稿第 V/VI 章为依据；不要用早期规划或全部研发里程碑代替用户最终选定内容。执行一次既定采集或修复局部脚本时不必重读整套案例。

这份案例重点提供的组织方式：

| 实验职责 | 当前精选案例的做法 | 新项目先考虑的问题 |
|---|---|---|
| 整体有效性 | 从实际运行过程到能力利用、局部差异、性能与重启复用，再检查学习成本和模型作用 | 方法实际改变了什么，变化如何产生价值，获取该能力花了多少代价？ |
| 关键机制 | 全部告警事件串起触发→记忆→下一决策→后续实测，再用撤销更新回放解释记忆作用 | 哪个内部机制改变了后续行为，怎样排除只是表面相关？ |
| 新条件适用性 | 固定核心模型/策略，换目标场景，区分初始化、校准、探索与复用 | 哪些能力可带过去，目标场景还需要哪些信息和交互？ |
| 真实平台表现 | 平台与实测过程、事前输出对照、逐次反馈更新及异常处理 | 实际环境里运行到哪一步，输出是否有用，系统是否根据新反馈改变行为？ |

先按新项目贡献映射这些职责，再确定实验标题、比较对象、指标与图表；不机械补齐四类。不含在线学习的项目可把记忆实验替换为对应关键模块的干预验证；没有真实平台资源时明确当前验证范围，不编造实测或把它设置成不必要的完成门槛。

优先产出一张精简实验结构表：`实验问题｜对应贡献｜设计/比较｜核心证据及图表｜可支持结论`。确定结构后按下文落实协议与核验，避免让审计清单淹没实验要讲的内容。

## 1. 每项实验先明确职责

按主张选择实验，不把“更多实验”本身当进展。

| 问题 | 合适证据 | 常见误用 |
|---|---|---|
| 能否工作 | 最小真实链路、集成运行、基本有效性 | 用编译成功替代运行 |
| 新机制是否起作用 | 中间决策、反馈事件、干预/消融 | 只展示最终总分 |
| 比较价值如何 | 强基线、共同条件/预算、成本与质量 | 仅展示最优一次 |
| 能否持续学习/适应 | 新反馈改变状态及后续行为 | 仅保存历史文件或触发一次开关 |
| 能否复用 | 新进程载入并完成实际任务 | 只比较保存文件是否相等 |
| 能否推广 | 新环境/条件下冻结与适应项清楚 | 用单个工作案例宣称普遍成立 |

主线只缺一个关键证据时，优先补它。没有必要为了论文外观机械增加消融、模型规模或新平台。

## 2. 先区分开发试验与正式评价

开发阶段用于查可行性、调接口、选择参数、确认基线能合理工作。正式评价用于回答冻结后的问题；两者可以迭代，但数据身份不能混淆。

正式运行前用短协议写清：

- 研究问题、方法版本、主要指标和必要次要指标。
- 独立实验单位、样本量依据、重复/随机化或配对方式。
- 数据划分、训练/验证/测试用途与防泄漏方式。
- 比较方法、调参机会、初始知识、初态、环境和资源差异。
- 预算起止、初始化/学习/恢复成本、终止条件和失败计分。
- 固定资产、种子、执行顺序、记录字段、产物位置。
- 异常判定、排除规则、补录或协议修订方式。
- 验收：怎样算实施合格，以及什么结果支持/不支持主张。

不强制固定重复次数，依据结论需要、变异、成本和独立性选择。资源只能支持案例时，仍可完成案例，但不把它包装成总体统计结论。

## 3. 数据可用性先于模型训练

检查样本来源、单位、时间轴、有效区间、重复、缺失和派生字段。

时序数据特别检查：

1. 训练/验证/测试按会话、个体、场景或其他真实独立单位划分。重叠窗口不能跨集合泄漏。
2. 窗口不跨越重置、圈界、条件切换或无效段；若跨越有方法学理由，要显式处理。
3. 归一化、特征选择和可训练处理只用训练数据拟合。
4. 推理只能使用决策时刻可得的信息。不得输入当时不可得的未来实测状态、实际控制或事后标签；候选动作、已知计划和当时生成的预测可以输入，但应标明性质，不冒充未来实测值。
5. 数据分片/重复导出不是新会话；同会话内多圈/窗口不自动是独立重复。

对失败、截尾、低需求和无效数据分别标状态。完整运行适合某类指标，不代表未完成段没有研究价值。排除必须有理由，不能默默把失败样本丢弃。

## 4. 区分命令、执行和结果

需要动作/决策因果链时记录：

```text
决策时可见上下文
→ 候选及评分
→ 选定动作/建议
→ 请求、接受与实际生效
→ 受限幅/保护影响后的实际暴露
→ 有效响应窗及数据质量
→ 事件判定
→ 状态/记忆更新
→ 后续实际行为或复验
```

“高请求值下无异常”只有在需求足够且真实执行时，才支持相应能力；被限速、低需求或数据缺失遮蔽时，只能说明这次观测未揭示问题。

对持续学习系统，区分单次观察、重复支持、待复验建议、预警约束和已复用状态。一次成功不自动等于可靠边界，一次告警也不自动证明所有更大动作都失败。

## 5. 公平对照与消融

公平不等于所有方法代码相同，而是比较条件及合理资源可解释。

- 给基线合理实现和开发调参机会，不设置显而易见的弱基线。
- 共同预算之外，报告初始知识差异。人工地图、预训练先验、额外标签不是免费等价输入。
- 共享环境、目标、有效性标准和终止口径；方法特有成本单列。
- 评估模型作用时，尽量保持记忆、动作空间和反馈规则等条件相同。
- 一次去掉多个模块得到的是联合消融，不能单独归因到每个模块。
- 反事实回放、移除更新后的决策重算与真实重跑，分别命名；回放没有产生新的物理结果。
- 最终保持/部署性能与包含学习成本的累计表现分开。两者可同时重要，但不能合并成一个普遍效率优势。

指标在看到正式结果后改变，应保留原主要分析并说明新分析为何属于探索性。不得挑出有利圈次/条件把事后选择伪装成预先规则。

## 6. 冻结、运行与审计

冻结的是会改变解释的资产：代码版本、配置、模型、数据划分、阈值、基线、计分及执行协议。可用版本号、提交、清单或哈希实现，按项目规模选择。

建议顺序：环境检查 → 小预算试运行 → 冻结 → 正式执行 → 有序关闭/恢复 → 提取与核查 → 汇总。需要现场设备时遵守该项目授权和操作规程，不把仿真许可延伸为真实设备许可。

每次运行保留最少必要 manifest：运行标识、起止时间、代码/配置/模型身份、环境、种子、输入输出、终止原因、状态、排除理由。关注实际运行版本，而不只是报告生成时的最新代码。

检查依据来自目标行为：动作一致性、决策重放、数据覆盖、独立单位和指标重算。不是每个项目都需要全量哈希或逐帧审计；按风险选择能抓住真实错误的核查。

## 7. 失败、修复与补录

先区分方法失败、数据问题、环境故障和执行器/评估基础设施故障。系统故障在科学分析和部署表现中可能有不同归属，两种口径都应解释，不能一律删除。

修复流程：

1. 保存原代码/配置、原始失败记录和已发生响应。
2. 定位原因，说明影响了哪些任务或样本。
3. 最小修复，针对机制复测，确认没有悄悄改方法或计分。
4. 建新冻结版本和旧→新对应账本，标记补录范围。
5. 分别报告主分析及保留原失败时的必要敏感性结果。

若修复改变方法逻辑、阈值或数据选择，视为新方法/协议版本。若同一测试结果用于下一版设计，该数据已参与开发，不能继续称为全新的独立测试。

停止条件应与实验风险和预算相称；不要无限重跑直到得到好看的结果。阶段是否完成由问题和验收决定，不由“本方法是否赢”决定。

## 8. 迁移、真实数据与执行模式

迁移先核对资产、坐标、单位、接口语义、支持域和目标条件。列出冻结源模型、允许目标校准、目标记忆初态和适应预算等实际项。目标标签参与校准就应记录，不能称完全零样本。

实测证据应分别标明：

| 模式 | 能直接支持什么 |
|---|---|
| 历史日志分析 | 记录中已发生行为及其关系 |
| 严格顺序回放 | 在给定过去信息下算法会产生什么建议/状态变化 |
| 在线只读/开环 | 现场信息时序下实际生成的输出；未接管控制 |
| 实际闭环控制 | 实际施加动作后产生的反馈与性能 |
| 模型反事实 | 模型对未执行动作的预测，需另行验证 |

这些模式可以同项目共存。根据运行记录和作者确认判定，不以 `replay.py` 等文件名推断全部部署。作者确认与本地可核验范围分别记录；建议接近后来的人工操作，也不能证明驾驶员采纳了建议。

## 9. 从结果收敛下一步

每次结论用“观察—解释—下一验证”区分事实与推断。重要机制解释如果尚未被干预证实，写为解释或假设。

结果不支持原主张时：检查是否有效实施；有效则如实收窄主张或提出有依据的新机制，保留原分析；无效则修复实施并记录版本。不要用文风优化代替科学修正。

更新证据表：主张、来源、方法版本、数据单位/条件、关键指标、支持程度、反例/缺口、下一动作。优先选择最可能改变研究决策的一项工作。

用户最终选定实验后，在项目记录标明最终位置、采用理由和相对开发计划的取舍。用户要求并入个人 skill 时，按[更新流程](skill-evolution.md)增加精选案例或修正已有条目；不把本轮所有运行记录逐条复制进个人手册。
